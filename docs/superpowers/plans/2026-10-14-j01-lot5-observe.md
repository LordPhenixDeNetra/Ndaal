# J01 lot 5 — Discipline et observabilité : plan d'implémentation

> **Pour les agents :** sous-compétence requise : superpowers:executing-plans (ou subagent-driven-development), tâche par tâche.
>
> **Pas d'étape de commit** : le responsable commite sur une branche `j01-lot5-observe` et ouvre une demande de fusion ; la CI fait foi.

**Objectif :** empêcher mécaniquement tout accès direct à l'horloge, au disque, au réseau et à l'aléa hors de `ndaal-io` (le déterminisme de la simulation en dépend), puis poser l'observabilité de base : journaux structurés à niveau modifiable à chaud, métriques sans verrou agrégées à la lecture, et politique d'erreurs et de paniques.

**Architecture :** le « lint maison » est la configuration `disallowed-methods` / `disallowed-types` de clippy (résolution des chemins par le compilateur, donc aussi les appels via `use`), plus une règle d'hygiène qui interdit de le désactiver hors des crates autorisées. `ndaal-observe` porte les journaux (`tracing`, `tracing-subscriber`), un registre de métriques maison par emplacements de thread (atomiques, sans verrou) et le gestionnaire de panique. `ndaal-common` porte `RequestId` et le guide des erreurs.

**Pile :** clippy 1.99 ; `tracing` 0.1.44, `tracing-subscriber` 0.3.23 (fonctionnalités `fmt`, `json`, `env-filter`, `registry`).

**Spécification :** [CAHIER_DES_TACHES.md](../../../CAHIER_DES_TACHES.md#j01--fondations-du-projet) T01.04, T01.10, T01.11, T01.24 ; [ARCHITECTURE.md](../../../ARCHITECTURE.md) §3 (règles de code), §16 (observabilité), §18.1 et §18.2 (erreurs, paniques) ; [DECISIONS.md](../../../DECISIONS.md) ADR-017, ADR-030 ; [EXPLOITATION.md §8.1](../../../EXPLOITATION.md#81-métriques-principales) ; [CLAUDE.md](../../../CLAUDE.md) §3.2, §4.2, §6.

## Contraintes globales

- Aucune crate ne lit l'horloge, le disque, le réseau ou l'aléa directement, sauf `ndaal-io` (ADR-017) ; outils de développement (`xtask`) et tests de `ndaal-io` exemptés explicitement.
- Journaux structurés, jamais de `println!` dans le code serveur ; aucun secret dans les journaux ni les métriques (CLAUDE.md §6).
- Métriques : chemin d'incrémentation sans verrou (atomiques), agrégation à la lecture (ARCHITECTURE §16) ; noms `ndaal_*` (EXPLOITATION §8.1).
- Binaires compilés avec `panic = "abort"` ; tests en déroulement de pile (ADR-030).
- Test d'abord ; mutation quand un test passe du premier coup.

## Décisions de périmètre (à valider avec le plan)

1. **Lint maison = configuration de clippy**, pas un outil écrit : `clippy.toml` liste les méthodes et types interdits (horloge, `std::fs`, `std::net`, `tokio::fs`/`net`/`time`, `getrandom`) ; `ndaal-io` les autorise par `#![allow(clippy::disallowed_methods, clippy::disallowed_types)]` avec justification. Une nouvelle règle d'hygiène (`xtask`) refuse cette exemption ailleurs que dans `ndaal-io` et `xtask`, pour qu'on ne puisse pas la contourner discrètement.
2. **Registre de métriques écrit pour Ndaal**, plutôt que la crate `metrics` citée par ARCHITECTURE §16 : l'exportateur Prometheus de `metrics` embarque un serveur HTTP et partage ses atomiques entre threads, alors que la spécification demande des métriques **locales par cœur agrégées à la lecture**. Une centaine de lignes : compteurs, jauges, histogrammes à seaux exponentiels, rendu au format texte Prometheus. ARCHITECTURE §16 est mise à jour. Les histogrammes HDR (précision fine des percentiles) viendront avec les bancs de performance (J07).
3. **Pas de serveur HTTP dans ce lot.** Le rendu Prometheus (`render() -> String`) est livré et testé ; son exposition sur `/metrics` se fera avec le frontal HTTP. Le critère de fin de T01.11 est donc atteint pour l'agrégation sans verrou, et **la partie « `/metrics` » est reportée** (T01.11 cochée, report inscrit dans POINTS_REPORTES.md avec la même échéance que le point de santé de T01.22, au lot 6).
4. **Identifiant de requête propagé par le contexte `tracing`** : un `RequestId` (128 bits, affiché en 32 caractères hexadécimaux) est porté par le champ `request_id` d'un span `request` ; tout journal émis pendant la requête, y compris celui du gestionnaire de panique, le contient. Pas de variable de thread : avec plusieurs tâches par cœur, elle désignerait la mauvaise requête.

## Points à surveiller en revue

1. **Contournement du lint** : appel via un `use` (`use std::time::Instant; Instant::now()`), via un alias, ou via un `allow` local dans une autre crate : détecté. Testé à la tâche 1.
2. **Niveau de journal invalide** (`"verbose"`) : erreur, le niveau courant est conservé. Testé à la tâche 2.
3. **Plus de threads que d'emplacements de métriques** : les valeurs restent exactes (emplacements partagés, toujours atomiques). Testé à la tâche 3.
4. **Noms et valeurs d'étiquettes à échapper** dans le format Prometheus (`"`, `\`, saut de ligne) : sortie valide. Testé à la tâche 3.
5. **Panique hors de toute requête** (au démarrage) : journal sans identifiant, arrêt quand même. Testé à la tâche 4.

### Tâche 1 : lint de discipline des effets de bord (T01.04)

**Fichiers :** Modifier `clippy.toml`, `crates/ndaal-io/src/lib.rs`, les tests d'intégration de `ndaal-io` qui utilisent `tokio::net` ou `std::fs` (en-tête `#![allow(...)]` justifié), `xtask/src/main.rs` (exemption), `xtask/src/hygiene/rust.rs` (nouvelle règle `ForbiddenLintBypass`).

- `clippy.toml` : `disallowed-methods` = `std::time::Instant::now`, `std::time::SystemTime::now`, `std::thread::sleep`, `std::fs::{read, read_to_string, write, read_dir, create_dir, create_dir_all, remove_file, remove_dir, remove_dir_all, rename, copy, metadata}`, `tokio::time::{sleep, sleep_until}`, `getrandom::{fill, u32, u64}` ; `disallowed-types` = `std::fs::{File, OpenOptions}`, `std::net::{TcpStream, TcpListener, UdpSocket}`, `tokio::fs::File`, `tokio::net::{TcpStream, TcpListener, UdpSocket}`. Chaque entrée porte `reason = "ADR-017: use ndaal-io"` ; les chemins de crates absentes de certaines crates (`tokio`, `getrandom`) ont `allow-invalid = true` si clippy le réclame.
- Règle d'hygiène `ForbiddenLintBypass` : un fichier `.rs` hors de `crates/ndaal-io/` et de `xtask/` qui contient `clippy::disallowed_methods` ou `clippy::disallowed_types` est signalé.

- [ ] **Tests d'abord :** (a) test unitaire de la règle d'hygiène : `crates/ndaal-kv/src/lib.rs` contenant `#![allow(clippy::disallowed_methods)]` → violation ; même texte dans `crates/ndaal-io/src/lib.rs` ou `xtask/src/main.rs` → rien ; (b) preuve du critère de fin, à la main : ajouter dans `ndaal-kv` une fonction qui appelle `std::time::Instant::now()` → `cargo clippy -p ndaal-kv -- -D warnings` échoue ; même chose avec `use std::time::Instant;` puis `Instant::now()`, et avec `std::fs::read("x")` ; retirer. Puis toute la chaîne de CLAUDE.md §11 reste verte (aucun faux positif dans le code existant).

### Tâche 2 : journaux structurés (T01.10)

**Fichiers :** Créer `crates/ndaal-observe/src/logs.rs` ; Modifier `crates/ndaal-observe/src/lib.rs`, `Cargo.toml` de la crate et de l'espace de travail.

**Interfaces (produit) :**
- `pub enum LogFormat { Text, Json }`
- `pub struct LogHandle` : `fn set_level(&self, directive: &str) -> Result<(), LogError>` (filtre `EnvFilter`, par exemple `"info"` ou `"ndaal_wal=debug,info"`) ; `fn level(&self) -> String`.
- `pub fn subscriber<W>(format: LogFormat, level: &str, writer: W) -> Result<(impl Subscriber + Send + Sync, LogHandle), LogError>` où `W: for<'a> MakeWriter<'a> + Send + Sync + 'static` : permet aux tests d'utiliser `tracing::subscriber::with_default` avec un tampon en mémoire.
- `pub fn init(format: LogFormat, level: &str) -> Result<LogHandle, LogError>` : installe le subscriber global sur la sortie standard.
- `pub enum LogError { InvalidLevel(String), AlreadyInitialized }` (`thiserror`).

- [ ] **Tests d'abord :** au niveau `info`, un `debug!` n'apparaît pas et un `info!` apparaît ; après `set_level("debug")` sur le même subscriber, le `debug!` apparaît (critère de fin : changement sans redémarrage) ; `set_level("verbose")` → `InvalidLevel`, et le niveau reste `info` ; format JSON : chaque ligne est un objet (`{` … `}`) avec les champs `"level"`, `"fields"` et les champs du span courant (`request_id` en tâche 4) ; format texte lisible.

### Tâche 3 : métriques locales et rendu Prometheus (T01.11)

**Fichiers :** Créer `crates/ndaal-observe/src/metrics.rs` (+ `metrics/render.rs` si le fichier dépasse 400 lignes).

**Interfaces (produit) :**
- `pub struct Registry` (clonable, partagé) : `counter(name, help, labels: &[(&str, &str)]) -> Counter`, `gauge(...) -> Gauge`, `histogram(name, help, labels, buckets: &[f64]) -> Histogram` ; le même nom et les mêmes étiquettes renvoient la même métrique ; `render(&self) -> String` (format texte Prometheus 0.0.4, une seule ligne `# HELP` et `# TYPE` par nom, séries triées).
- `Counter::increment(&self, by: u64)` ; `Gauge::set(&self, v: i64)` et `add(&self, d: i64)` ; `Histogram::observe(&self, v: f64)`.
- `pub const LATENCY_BUCKETS: [f64; 25]` : 1 µs × 2^k, k = 0..24 (1 µs à ~16,8 s), en secondes.
- Implémentation : chaque compteur et histogramme possède `SLOTS = 64` emplacements (`AtomicU64`, alignés sur 64 octets pour éviter le faux partage) ; chaque thread reçoit à sa première écriture un numéro d'emplacement (`thread_local!` + compteur global modulo `SLOTS`) ; écriture en `Relaxed`, lecture = somme des emplacements. Aucun verrou sur le chemin d'écriture ; le registre (création des métriques, rendu) peut utiliser un `Mutex`.

- [ ] **Tests d'abord :** 8 threads × 10 000 incréments → `render` montre 80 000 ; 100 threads (plus que `SLOTS`) → valeur exacte ; histogramme : `_bucket{le="..."}` cumulés, `_sum`, `_count`, `+Inf` = `_count` ; deux `counter` avec le même nom et les mêmes étiquettes partagent la valeur, avec des étiquettes différentes donnent deux séries ; échappement : valeur d'étiquette `a"b\c` + saut de ligne → `a\"b\\c\n` ; `# HELP` et `# TYPE` une seule fois par nom ; sortie triée et stable (même registre → même texte).

### Tâche 4 : erreurs, identifiant de requête et paniques (T01.24)

**Fichiers :** Modifier `Cargo.toml` (profils), `crates/ndaal-common/src/error.rs` (guide), Créer `crates/ndaal-common/src/request.rs`, `crates/ndaal-observe/src/panic.rs`, `crates/ndaal-observe/src/bin/panic-probe.rs` (binaire de test), `crates/ndaal-observe/tests/panic.rs`.

**Interfaces (produit) :**
- `[profile.dev]` et `[profile.release]` : `panic = "abort"` (les tests restent en déroulement, comportement de Cargo).
- `ndaal_common::request::RequestId([u8; 16])` : `from_random_bytes`, `Display` en 32 caractères hexadécimaux minuscules, `FromStr` ; constante de convention `REQUEST_SPAN = "request"` et champ `request_id`.
- `ndaal_observe::panic::install(registry: &Registry)` : remplace le gestionnaire de panique ; il émet `tracing::error!` avec le message, l'emplacement et la pile d'appels (`Backtrace::force_capture`), incrémente `ndaal_panics_total`, vide la sortie standard et d'erreur ; puis l'arrêt suit (`panic = "abort"`).
- Guide des erreurs : documentation du module `ndaal_common::error` reprenant ARCHITECTURE §18.1 et §18.2 (cause conservée, une seule journalisation, message client sans détail interne, identifiant de requête, panique = bogue).

- [ ] **Tests d'abord (`tests/panic.rs`, critère de fin) :** lancer `panic-probe request` (`env!("CARGO_BIN_EXE_panic-probe")`), qui initialise les journaux JSON, installe le gestionnaire, entre dans un span `request` avec un identifiant connu puis panique : le processus se termine en échec (arrêt, pas de code 0), la sortie contient le message, l'identifiant de requête et une pile d'appels (plusieurs lignes de cadres) ; `panic-probe startup` (panique hors requête) : même chose sans `request_id`. Tests de `RequestId` : aller-retour, format, refus d'une chaîne invalide.
