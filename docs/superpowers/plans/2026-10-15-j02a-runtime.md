# J02-A — Runtime thread-per-core : plan d'implémentation

> **Pour les agents :** sous-compétence requise : superpowers:executing-plans (ou subagent-driven-development), tâche par tâche.
>
> **Pas d'étape de commit** : le responsable commite sur une branche `j02a-runtime` et ouvre une demande de fusion. Le compte rendu donne les commandes git **et le contenu du formulaire de demande de fusion**.

**Objectif :** la crate `ndaal-runtime`, dotée de :
- l'attribution des cœurs aux classes de charge ;
- une messagerie bornée entre cœurs, en version réelle (`rtrb`) et en version simulée ;
- un thread par cœur, chacun avec un runtime `tokio` `current_thread`, épinglé quand le système le permet ;
- la configuration `[runtime]`, les métriques, un micro-banc d'aller-retour et un scénario de simulation `cross_core`.

**Architecture :** quatre modules de `ndaal-runtime`, décrits dans la spécification §3.
- `layout` : une fonction pure.
- `mailbox` : le trait, les types communs, la comptabilité des places réservées et la table des requêtes en attente, partagés par les deux implémentations.
- `mailbox::real` et `mailbox::sim` : les deux implémentations de la messagerie.
- `real` : les threads, l'épinglage, le démarrage et l'arrêt.

Le runtime n'est pas encore branché sur `ndaal server` : la première couche qui en a besoin est la partition (sous-projet E).

**Pile :** `tokio` (`rt`, `sync`, `macros`), `rtrb` 0.4.0, `core_affinity` 0.8.3, `criterion`.

**Spécification :** [docs/superpowers/specs/2026-10-15-j02a-runtime-design.md](../specs/2026-10-15-j02a-runtime-design.md), validée le 2026-10-15. En cas de doute, elle fait foi.

## Contraintes globales

- **Effets de bord (ADR-017).** Aucune lecture directe d'horloge ni d'aléa dans `ndaal-runtime` : le temps passe par `ndaal_io::Clock` (`SystemClock` en réel, `SimClock` en simulé), l'aléa par `ndaal_io::Rng`. `std::thread::spawn` est permis, puisqu'il n'est pas interdit par `clippy.toml`.
- **`unsafe`.** Aucun bloc `unsafe` n'est prévu : `rtrb` et `core_affinity` le contiennent. Si une étape semble en exiger un, c'est une décision à consigner, avec `// SAFETY:`.
- **Code propre à un système.** Il reste dans `ndaal-runtime`, derrière `cfg!(target_os = "macos")` pour l'épinglage (CLAUDE.md §4.8).
- **Délais :**
  - démarrage : `START_TIMEOUT = 5 s` ;
  - arrêt : `STOP_TIMEOUT = 10 s` ;
  - attente active par défaut : `runtime.idle_spin = 50us`.
- **Simulation.** Délai de livraison tiré uniformément dans `0..=SIM_MAX_DELIVERY_DELAY` (50 µs de temps virtuel), par le générateur nommé `"runtime"`.
- **Métriques**, avec ces noms exacts :
  - `ndaal_runtime_queue_full_total{to}` ;
  - `ndaal_runtime_core_parks_total{core}` ;
  - `ndaal_runtime_replies_dropped_total` ;
  - `ndaal_runtime_cores{class}`.
- **Taille des fichiers.** 400 lignes visées : `mailbox` est découpé en `mod.rs`, `shared.rs`, `real.rs` et `sim.rs`.
- **Code.** ASCII, aucun emoji, test d'abord. Textes de la CLI par Fluent, en anglais et en français.

## Précision sur la spécification (consignée au registre)

La spécification §3.1 règle 5 dit « la classe que la table désigne (ligne inférieure entre deux lignes) ». Elle est appliquée par une **chaîne de repli** unique, qui reproduit exactement les lignes 2, 4 et 8 de la table et couvre aussi les valeurs imposées :
- `vector` → `shard` ;
- `transfer` → `vector` → `shard` ;
- `background` → `transfer` → `vector` → `shard` ;
- `io` → `shard`.

Une classe sans cœur dédié est placée sur le **premier** cœur de la première classe de sa chaîne qui en a.

## Points à surveiller en revue

1. **Réveil perdu** : un message publié pendant que le destinataire passe en sommeil est toujours reçu. Testé à la tâche 4 (100 000 essais avec `idle_spin = 0`).
2. **Interblocage croisé** : deux cœurs qui s'envoient chacun autant de requêtes que la capacité le permet finissent tous deux. Testé à la tâche 3 (contrat commun) et à la tâche 6 (`cross_core`).
3. **`Replier` abandonné** : sans réponse, `Pending` se résout en `Err(Dropped)`, la place est libérée et le compteur `ndaal_runtime_replies_dropped_total` augmente. Testé à la tâche 3.
4. **Arrêt pendant que des requêtes sont en attente** : les `Pending` se résolvent en `Err(ShuttingDown)`, aucune n'attend indéfiniment, et `shutdown()` se termine en moins de 10 s. Testé à la tâche 5.
5. **`runtime.cores.total` supérieur aux cœurs autorisés** (conteneur limité, `taskset`) : erreur de configuration qui nomme la clé, sans démarrer de thread. Testé à la tâche 2.

### Tâche 2 : `layout`

**Fichiers :** créer `crates/ndaal-runtime/src/layout.rs` ; modifier `crates/ndaal-runtime/src/lib.rs` et `crates/ndaal-runtime/Cargo.toml`.

**Interfaces (produit) :**
- `pub enum Class { Shard, Vector, Transfer, Background, Io }`, dans cet ordre, qui sert aussi à départager les arrondis.
- `pub struct CoreSpec { pub cpu: usize, pub primary: Class, pub shared: Vec<Class> }`.
- `pub struct Layout { pub cores: Vec<CoreSpec> }`, avec `pub fn count(&self, class: Class) -> usize` qui compte les cœurs dédiés.
- `pub enum LayoutError { TooManyCores { key: &'static str, requested: usize, available: usize }, NoShard, NoCpu }`.
- `pub fn assign(available: &[usize], config: &CoresConfig) -> Result<Layout, LayoutError>` :
  - `available` est la liste des processeurs autorisés, dans l'ordre ;
  - les cœurs sont attribués dans l'ordre des classes, sur les processeurs dans l'ordre ;
  - les classes partagées suivent la chaîne de repli.
- Table, au format `(shard, vector, transfer, background, io)` :
  - 2 → (1,0,0,0,1) ;
  - 4 → (2,1,0,0,1) ;
  - 8 → (3,3,1,0,1) ;
  - 16 → (6,6,2,1,1) ;
  - 64 → (20,32,6,4,2).
- Arrondi : méthode du plus grand reste, ex æquo départagés par l'ordre de `Class`.

- [ ] **Tests d'abord :**
  - `table_rows_are_exact` : les cinq lignes ;
    - à 2 cœurs, le cœur 0 porte `shard`, avec `shared` = `[Vector, Transfer, Background]` ;
    - à 4 cœurs, `transfer` et `background` partagent le cœur `vector` ;
    - à 8 cœurs, `background` partage le cœur `transfer`.
  - `interpolation_examples` :
    - 3 → (2,0,0,0,1) ;
    - 12 → (5,5,1,0,1), avec `background` partagé sur `transfer` ;
    - 100 → (31,50,10,6,3) ;
    - 128 → (40,64,12,8,4).
  - `one_core` : `shard`, avec `shared` = `[Vector, Transfer, Background, Io]`.
  - `invariants_1_to_256` : la somme des cœurs dédiés égale le total, il y a au moins un `shard`, chaque classe est soit dédiée, soit partagée sur exactement un cœur, et chaque processeur est utilisé une fois.
  - `overrides` : à 16 cœurs, `shard = 10` donne 10 cœurs `shard` et 6 répartis entre les autres ; `shard = 0` donne `NoShard` ; la somme des valeurs imposées supérieure aux cœurs donne `TooManyCores` ; `total = Fixed(32)` sur 8 processeurs donne `TooManyCores { key: "runtime.cores.total" }`.

### Tâche 3 : messagerie — types communs, implémentation simulée, contrat

**Fichiers :** créer `crates/ndaal-runtime/src/mailbox/{mod.rs, shared.rs, sim.rs}` et `crates/ndaal-runtime/tests/{mailbox_contract.rs, common/mod.rs}`.

**Interfaces (produit, dans `mailbox`) :**
- `pub struct CoreId(pub u16)`.
- `pub enum SendError<M> { Full(M), ShuttingDown(M) }`.
- `pub enum Incoming<M, R> { Message { from: CoreId, msg: M }, Request { from: CoreId, msg: M, replier: Replier<R> } }`.
- `pub enum ReplyError { Dropped, ShuttingDown }`.
- `pub struct Pending<R>` implémente `Future<Output = Result<R, ReplyError>>`.
- `pub struct Replier<R>`, avec `pub fn reply(self, value: R)`. Sur `Drop` sans réponse, il livre `Dropped` et incrémente `ndaal_runtime_replies_dropped_total`.
- `pub trait Mailbox<M, R>` :
  - `fn core(&self) -> CoreId` ;
  - `fn try_send(&self, to: CoreId, msg: M) -> Result<(), SendError<M>>` ;
  - `fn request(&self, to: CoreId, msg: M) -> Result<Pending<R>, SendError<M>>` ;
  - `async fn recv(&self) -> Option<Incoming<M, R>>`, qui rend `None` une fois l'arrêt demandé et les files vidées ;
  - `fn shutdown(&self)`, qui marque le cœur « en arrêt » et rend `ShuttingDown` à ses `Pending`.
- `shared.rs` : la comptabilité des places réservées par destinataire (au plus `capacity` requêtes en cours) et la table des `Pending` par numéro de requête. Ces deux mécanismes servent aux deux implémentations.
- `pub fn sim_mailboxes<M: 'static, R: 'static>(cores: u16, capacity: usize, clock: SimClock, rng: Xoshiro256PlusPlus, registry: &Registry) -> Vec<SimMailbox<M, R>>` :
  - les files de cette implémentation sont des `VecDeque` de capacité `capacity` ;
  - chaque message porte son instant de livraison, `max(dernier de la paire, maintenant + délai tiré)`, ce qui garde l'ordre FIFO par paire.
- `tests/common/mod.rs` : `pub async fn contract<B: Mailbox<u32, u32>>(boxes: &[B])`, qui exécute tout le contrat, sur le modèle de `crates/ndaal-io/tests/common/mod.rs`.

- [ ] **Tests d'abord**, sur les boîtes simulées, avec 3 cœurs et une capacité de 2 :
  - `fifo_per_pair` : 2 messages du cœur 0 vers le cœur 1 sont reçus dans l'ordre, et `from` vaut le cœur 0.
  - `full_returns_the_message` : un 3e `try_send` rend `Full(3)`, et `ndaal_runtime_queue_full_total{to="1"}` vaut 1.
  - `reply_always_delivered` : 2 requêtes du cœur 0 vers le cœur 1 trouvent leur réponse.
  - `request_without_reply_slot_is_refused` : une 3e `request`, sans réponse aux deux premières, rend `Full`.
  - `dropped_replier` : `Pending` donne `Err(Dropped)`, puis une nouvelle `request` est acceptée.
  - `shutdown` : `ShuttingDown` à l'envoi, `Err(ShuttingDown)` pour les `Pending`, `recv` rend `None` une fois les files vidées.
  - `crossed_requests_do_not_deadlock` : le cœur 0 et le cœur 1 s'envoient chacun 2 requêtes, et les 4 réponses arrivent.
  - `same_seed_same_delivery` : deux exécutions avec la même graine donnent le même ordre de réception, entre émetteurs différents.

### Tâche 4 : messagerie réelle (`rtrb`)

**Fichiers :** créer `crates/ndaal-runtime/src/mailbox/real.rs` et `crates/ndaal-runtime/tests/mailbox_real.rs` ; modifier `Cargo.toml` (`rtrb = "0.4.0"`).

**Interfaces (produit) :**
- `pub struct Endpoint<M, R>` est `Send`, pour être construit sur le thread principal puis déplacé vers le thread de son cœur.
- `pub fn real_endpoints<M: Send, R: Send>(cores: u16, capacity: usize, registry: &Registry) -> Vec<Endpoint<M, R>>`.
- `impl Endpoint { pub fn into_mailbox(self, idle_spin: Duration, clock: SystemClock) -> RealMailbox<M, R> }` s'appelle sur le thread du cœur. `RealMailbox` n'est pas `Send` (état `Rc` ou `RefCell` propre au cœur).
- Il y a une file `rtrb` par paire et par sens pour les messages, et une pour les réponses.
- Réveil : `Arc<CoreWaker>`, avec un drapeau `AtomicBool` « endormi » et un `tokio::sync::Notify`. Le destinataire lève le drapeau puis **revérifie ses files** avant d'attendre ; l'émetteur publie le message, puis lit le drapeau et ne réveille que s'il est levé (ordre `SeqCst`). Chaque mise en sommeil incrémente `ndaal_runtime_core_parks_total{core}`.
- Attente active : `recv` surveille les files pendant `idle_spin`, mesuré par `SystemClock::monotonic`, en appelant `tokio::task::yield_now()` entre deux surveillances, puis s'endort.

- [ ] **Tests d'abord :**
  - `contract_on_real_mailboxes` : le contrat de la tâche 3 sur des boîtes réelles, utilisées depuis un seul thread `current_thread` ;
  - `wake_is_never_lost` : deux threads, et `idle_spin = 0` pour que chaque message trouve le destinataire endormi ou sur le point de l'être ; 100 000 requêtes, chacune doit recevoir sa réponse en moins de 1 s (délai mesuré par `SystemClock`), sinon le test échoue en donnant le numéro de l'essai ;
  - `spin_avoids_parking` : avec `idle_spin = 50ms` et 1 000 requêtes rapprochées, `core_parks_total` reste à 0.

### Tâche 5 : threads, épinglage, démarrage et arrêt

**Fichiers :** créer `crates/ndaal-runtime/src/real.rs` et `crates/ndaal-runtime/tests/runtime.rs` ; modifier `Cargo.toml` (`core_affinity = "0.8.3"`, et les fonctionnalités `rt`, `sync` et `macros` de `tokio`).

**Interfaces (produit) :**
- `pub struct RuntimeOptions { pub pin: bool, pub idle_spin: Duration, pub capacity: usize, pub registry: Registry }`.
- `pub struct CoreContext<M, R> { pub id: CoreId, pub spec: CoreSpec, pub mailbox: RealMailbox<M, R> }`.
- `pub fn allowed_cpus() -> Vec<usize>` : `core_affinity::get_core_ids()`, ou, à défaut, `0..available_parallelism`.
- `pub fn Runtime::start<M, R, F, Fut>(layout: &Layout, options: RuntimeOptions, factory: F) -> Result<Runtime, StartError>`.
  - Bornes : `F: Fn(CoreContext<M, R>) -> Fut + Send + Sync + 'static`, `Fut: Future<Output = ()> + 'static`, `M: Send + 'static` et `R: Send + 'static`.
  - Chaque thread construit son runtime, épingle si `pin` vaut vrai et que le système n'est pas macOS, signale qu'il est prêt, puis exécute `factory(ctx)` jusqu'à sa fin.
- `pub enum StartError { Spawn(io::Error), Pin { cpu: usize }, Timeout }`. Sur erreur, les threads déjà lancés sont arrêtés avant le retour.
- `pub fn Runtime::shutdown(self) -> Result<(), ShutdownError>`, avec `ShutdownError { stuck: Vec<CoreId> }`. Il appelle `shutdown()` sur chaque boîte (via un `Arc` d'arrêt partagé), puis attend que tous les threads se terminent, `STOP_TIMEOUT` au plus.
- Sous macOS, l'avertissement `runtime pinning unsupported` est journalisé une seule fois.
- Les jauges `ndaal_runtime_cores{class}` sont renseignées.

- [ ] **Tests d'abord :**
  - `starts_and_stops_four_cores` : 4 cœurs, chacun renvoie son `CoreId` par un canal `std::sync::mpsc`, et `shutdown` rend `Ok` en moins de 10 s.
  - `pinned_on_linux` (`#[cfg(target_os = "linux")]`) : dans chaque cœur, `core_affinity::get_core_ids()` rend exactement `[spec.cpu]`.
  - `macos_runs_unpinned` (`#[cfg(target_os = "macos")]`) : le démarrage réussit avec `pin = true`.
  - `shutdown_resolves_pending_requests` : le cœur 1 ne répond jamais. Le `Pending` du cœur 0 se résout en `Err(ShuttingDown)` et `shutdown` rend `Ok`.
  - `stuck_core_is_reported` : un cœur dont le futur ignore l'arrêt (boucle sur `yield_now`) donne `Err(ShutdownError { stuck: [CoreId(1)] })`, après 10 s au plus.
  - `cores_gauge` : après le démarrage, `ndaal_runtime_cores{class="shard"}` égale `layout.count(Class::Shard)`.

### Tâche 6 : micro-banc et scénario de simulation `cross_core`

**Fichiers :**
- créer `crates/ndaal-runtime/benches/round_trip.rs` et `crates/ndaal-sim/src/cross_core.rs` ;
- modifier :
  - `crates/ndaal-runtime/Cargo.toml` (`[[bench]]`) ;
  - `crates/ndaal-sim/src/{lib.rs, main.rs}` et `crates/ndaal-sim/Cargo.toml` (dépendance `ndaal-runtime`) ;
  - `.github/workflows/nightly.yml`.

**Interfaces :**
- Banc `runtime/round_trip` :
  - 2 cœurs, `idle_spin = 1ms`, le cœur 1 renvoie en écho ;
  - `iter_custom` mesure N allers-retours sur le cœur 0 avec `SystemClock`, puis rend la durée par un canal.
- `pub fn cross_core(seed: u64, cores: u16, requests: u32) -> CrossCoreReport` :
  - capacité 2 ;
  - chaque cœur envoie `requests` requêtes `(from, seq)` à des cœurs choisis par la graine, et se met en sommeil 10 µs (temps virtuel) sur `Full` ;
  - chaque destinataire renvoie `(from, seq)`.
- `CrossCoreReport { outcome, sent, replied, mismatched, fingerprint }`.
- `pub fn cross_core_result(seed: u64) -> SeedResult` : 4 cœurs, 50 requêtes chacun ; réussite si `Finished`, si `replied == sent == 200` et si `mismatched == 0`.
- `ndaal-sim sweep` joue **les deux scénarios** pour chaque graine.
  - `finished` vaut la conjonction des deux, l'empreinte combine les deux, et `detail` nomme le scénario en échec.
  - Dans `nightly.yml`, le titre du ticket devient « sim: failing seeds ».

- [ ] **Tests d'abord :**
  - `cross_core_completes` : 50 graines, toutes réussies ;
  - `cross_core_is_reproducible` : la graine 7 donne la même empreinte deux fois ;
  - `sweep_covers_both_scenarios` : un `cross_core_result` en échec, injecté via `sweep`, apparaît avec le nom du scénario ;
  - `cargo bench -p ndaal-runtime -- --test` réussit, puis la mesure locale est consignée dans le registre.
