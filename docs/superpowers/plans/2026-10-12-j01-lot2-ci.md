# J01 lot 2 — CI GitHub Actions : plan d'implémentation

> **Pour les agents :** sous-compétence requise : superpowers:executing-plans (ou subagent-driven-development), tâche par tâche.
>
> **Pas d'étape de commit** : le responsable commite et pousse lui-même (`CLAUDE.local.md`). Ce lot ne peut être prouvé que sur GitHub : il se termine par des commandes git (branche, push, demande de fusion) et par la lecture des exécutions via l'API publique de GitHub.

**Objectif :** chaque demande de fusion vers `main` déclenche une CI qui exécute toutes les vérifications du lot 1 sur Linux x86_64, Linux arm64, macOS et Windows, vérifie la signature DCO et publie un rapport de couverture ; `main` est protégée.

**Architecture :** un seul workflow `ci.yml`. Chaque vérification reste un script du dépôt (ADR-028 : la CI appelle `scripts/`, rien n'est écrit seulement dans le YAML). Les outils sont installés par `scripts/install-tools.sh` aux versions de `scripts/tools.versions`, comme en local, et mis en cache.

**Pile :** GitHub Actions, `actions/checkout` v7.0.1, `Swatinem/rust-cache` v2.9.2, `actions/upload-artifact` v7.0.2, `cargo-nextest` 0.9.148, `cargo-llvm-cov` 0.9.1, `actionlint` (vérification locale des workflows, en conteneur).

**Spécification :** [CAHIER_DES_TACHES.md, J01](../../../CAHIER_DES_TACHES.md#j01--fondations-du-projet) (T01.03, T01.13, T01.20, T01.21, et la partie CI de T01.02, T01.16, T01.19, T01.25), [STRATEGIE_DE_TESTS.md §13](../../../STRATEGIE_DE_TESTS.md#13-intégration-continue), [ADR-028](../../../DECISIONS.md#adr-028--cicd-sur-github-actions), [CLAUDE.md](../../../CLAUDE.md) §4.12 et §10.

## Contraintes globales

- Actions tierces épinglées par **empreinte de commit** (pas par étiquette), avec l'étiquette en commentaire : `actions/checkout@3d3c42e5aac5ba805825da76410c181273ba90b1 # v7.0.1`, `Swatinem/rust-cache@6323deb102c322ba6fcbdcafc7e3dddab59af2b6 # v2.9.2`, `actions/upload-artifact@cf430e030ddbb5b0abf93d22962f4752f3646cd9 # v7.0.2`.
- Permissions du jeton : `contents: read` au niveau du workflow, rien d'autre.
- `concurrency` : une exécution par branche, la précédente annulée.
- Aucun secret utilisé ; rien ne s'exécute avec les droits d'écriture sur une demande venant d'un fork.
- Fichiers `.yml` en ASCII (CLAUDE.md §4.7).
- Durée cible : moins de 15 minutes par exécution avec le cache chaud (T01.03).

## Décisions de périmètre (à valider avec le plan)

1. **Pas de `nightly.yml` ni de `docs.yml` dans ce lot.** Le critère de fin de T01.20 ne porte que sur `ci.yml`, la protection de `main` et Dependabot ; `nightly.yml` n'aurait rien à exécuter (ni simulation, ni fuzzing, ni bancs n'existent encore) et `docs.yml` dépend du site mdBook (T01.17). Ils seront créés par T01.09/T01.14 et T01.17.
2. **Pas de tâche MSRV séparée.** La MSRV (1.99) est la version figée de `rust-toolchain.toml` : toute compilation en CI la vérifie déjà.
3. **Pas de seuil de couverture.** Les crates sont vides ; T01.13 demande un rapport publié. Les seuils ENF-QUAL-01 s'appliqueront quand il y aura du code.
4. **Relecture obligatoire avant fusion : 0 approbation tant que vous êtes seul.** GitHub n'autorise pas l'auteur d'une demande de fusion à l'approuver lui-même : exiger une approbation bloquerait toutes vos fusions. La protection exige donc une demande de fusion et une CI verte, avec 0 approbation, à passer à 1 dès l'arrivée d'un second mainteneur (inscrit dans POINTS_REPORTES.md).

## Points à surveiller en revue

1. **Scripts Bash sous Windows** : sur `windows-latest`, `shell: bash` (Git Bash) doit être explicite pour chaque étape qui appelle `scripts/*.sh`.
2. **Chemins et fins de ligne sous Windows** : le checkout ne doit pas convertir en CRLF (protégé par `.gitattributes`, vérifié par l'hygiène qui tourne aussi sur Windows).
3. **Demande de fusion contenant un commit non signé, ou signé avec une autre adresse que l'auteur** : la vérification DCO doit échouer et nommer le commit.
4. **Commits de fusion et commits de Dependabot** : Dependabot ne signe pas ses commits ; la vérification DCO doit les accepter sans désactiver le contrôle pour les humains.
5. **Cache froid** (première exécution, ou après changement de `tools.versions`) : la compilation de `cargo-deny`, `cargo-nextest` et `cargo-llvm-cov` doit rester dans un délai raisonnable ; mesurer et consigner.

### Tâche 3 : workflow `ci.yml` (T01.03, T01.13, T01.20, T01.21)

**Fichiers :**
- Créer : `.github/workflows/ci.yml`, `.github/dependabot.yml`

**Interfaces :**
- Consomme : `scripts/install-tools.sh`, `scripts/check-hygiene.sh`, `scripts/check-deny.sh`, `scripts/check-dco.sh`.

Structure de `ci.yml` :

| Élément | Valeur |
|---|---|
| Déclencheurs | `pull_request` vers `main` ; `push` sur `main` |
| `permissions` | `contents: read` |
| `concurrency` | `group: ci-${{ github.ref }}`, `cancel-in-progress: true` |
| Travail `checks` (`ubuntu-latest`) | checkout, cache, `install-tools.sh`, `cargo fmt --all --check`, `cargo clippy --workspace --all-targets -- -D warnings`, `check-hygiene.sh`, `check-deny.sh` |
| Travail `test` (matrice) | `ubuntu-latest`, `ubuntu-24.04-arm`, `macos-latest`, `windows-latest` ; `fail-fast: false` ; checkout, cache (clé incluant le système), `install-tools.sh`, `cargo clippy --workspace --all-targets -- -D warnings`, `cargo nextest run --workspace` |
| Travail `dco` (seulement sur `pull_request`) | checkout avec `fetch-depth: 0`, `check-dco.sh ${{ github.event.pull_request.base.sha }} ${{ github.event.pull_request.head.sha }}` |
| Travail `coverage` (`ubuntu-latest`, seulement sur `pull_request`) | `cargo llvm-cov nextest --workspace --lcov --output-path lcov.info` et `--summary-only` ; résumé écrit dans `$GITHUB_STEP_SUMMARY` ; `lcov.info` publié comme artefact (`upload-artifact`) |

Toutes les étapes qui appellent un script : `shell: bash`. Les étapes `run` ne contiennent qu'un appel de commande ; aucune logique de vérification dans le YAML.

`dependabot.yml` : écosystèmes `cargo` (répertoire `/`) et `github-actions` (répertoire `/`), fréquence hebdomadaire, préfixe de message `build(deps)`.

- [ ] **Étape 1 : écrire `ci.yml` et `dependabot.yml`.**

Run : `docker run --rm -v "<dépôt>:/repo" -w /repo rhysd/actionlint:<version épinglée par empreinte> -color` (mêmes précautions de chemin que `check-linux.sh`).
Attendu : aucune erreur. Puis introduire volontairement une faute (`runs-on: ubunt-latest` ou une expression `${{ }}` invalide) → actionlint la signale ; la retirer.
